# 技术说明

## 模型与量化

模型是 `Xenova/bge-small-zh-v1.5`，对应上游 `BAAI/bge-small-zh-v1.5`，维度 512。运行时是 Transformers.js 3.8.1，`dtype: "q8"` 会加载 `onnx/model_quantized.onnx`。

量化用的是仓库里已经发布的 ONNX，不是本项目再跑一遍量化脚本。`quantize_config.json` 写的是按通道、`weight_type: QInt8`，权重量成 8 位整数。这是 INT8 方案。FP16 用同一仓库的 `onnx/model_fp16.onnx`，只作对照。

体积只算这一份 ONNX 权重，不算三种精度共用的 tokenizer。2026-10-28 实测：

| 文件 | 字节 | 相对 FP32 |
| --- | ---: | ---: |
| onnx/model.onnx | 94851877 | 1 |
| onnx/model_fp16.onnx | 47497427 | 2.00 倍压缩 |
| onnx/model_quantized.onnx | 24010842 | 3.95 倍压缩 |

压缩比 = FP32 字节数 / 该精度字节数。短查询检索时，query 前加 `为这个句子生成表示以用于检索相关文章：`，段落不加。三种精度用同一条规则。换模型就必须新建集合，维度写在集合上，对不上会直接拒绝写入。

检索质量用 `eval/queries.json` 的 10 条查询，每条 1 个相关 `doc_id`。Recall@5、nDCG@5 按文档算，一段命中算这篇命中，相关性是二值。三组 Recall@5 都是 1.000。nDCG@5：FP32 + WebGPU 是 1.000，INT8 + WASM 也是 1.000，INT8 在界面报 WebGPU 时是 0.889。那 0.111 的下降只出现在 WebGPU 这条路上，10 条里有 3 条正确文档从第 1 名掉到第 2 名：`q-refresh`、`q-webgpu`、`q-hybrid`。同一份 INT8 权重改走 WASM 后，这 3 条又回到第 1 名。文档向量是第一次 INT8 导入时写进 `kb_bge_small_zh_v15_q8` 的，后面遇到同一个 id 会跳过写入。WASM 这两次测到的是 WASM 查询向量对上那批已经入库的文档，文档没有用 WASM 重写。这组样例太容易，换更难的语料，WASM 上的 INT8 也可能看出和 FP32 的差距。原始记录在 `eval/edge-webgpu-fp32.json`、`eval/edge-webgpu-q8.json`、`eval/edge-webgpu-q8-repeat.json`、`eval/edge-wasm-q8.json`、`eval/edge-wasm-q8-repeat.json`。

## 端侧运行

推理在 Web Worker 里。先 `navigator.gpu.requestAdapter()`，有适配器就 `device: "webgpu"`，没有或建 pipeline 失败就改 `device: "wasm"`。右上角写当前精度和后端。WASM 多线程依赖这两个响应头：`Cross-Origin-Opener-Policy: same-origin`、`Cross-Origin-Embedder-Policy: require-corp`。ONNX Runtime 的 pthread 在这个页面里会把会话创建卡住，所以线程数固定为 1。页面没隔离时本来也只能单线程。

ONNX Runtime 的 wasm 从本机 `/ort/` 读，不走 jsDelivr。模型不走 Hugging Face。

同一份 INT8 模型，强制 `?device=wasm` 后，预热查询向量化中位数是 17 ms，复测仍是 17 ms。界面报 WebGPU 时是 85 ms，大约慢 5 倍，超出重复误差。INT8 没有在这台 RTX 4060 的 WebGPU 上变快，界面上的 WebGPU 不能当成整数算子已经在显卡上加速。FP32 走 WebGPU 是 8 ms，仍是三条里最快的。页面会先等 WebGPU 45 秒，超时再改 WASM。

## seekdb

`seekdb@1.4.0`。默认嵌入式，目录 `data/seekdb`。设置 `SEEKDB_HOST` 后改连本机 server。集合用堆表，字段是 id、document、embedding、metadata。向量索引 HNSW，距离 cosine，维度 512。全文索引显式指定 `ngram`，`ngram_token_size=2`。`embeddingFunction` 设为 `null`，不安装 `@seekdb/default-embed`。

混合检索只调用一次 `collection.hybridSearch`：`query.whereDocument.$contains` 变成 document 上的 `query_string`，`knn.queryEmbeddings` 用浏览器传来的向量，融合是 `rank.rrf`，当前 `rankWindowSize=40`、`rankConstant=60`。整句和关键词哪种喂给全文更合适，还没做 A/B，所以这两个数先当默认值，不当成调优结论。

2026-10-28 用三条手工向量在嵌入式库 `data/smoke` 上跑过一次：`VERSION()` 是 `5.7.25-OceanBase seekdb-v1.4.0.0`，`refresh_index` 真的被调用，耗时 8045 ms，随后 `hybridSearch` 59 ms，第一条是预期文档。这只证明数据库这条路通了，不能填进下面的浏览器性能表。关闭进程时嵌入式库打过 `OB_ABORT`，主流程已经返回。

写入按批 `add`。全部写完后调用一次 `collection.refresh_index()`，也就是 `CALL dbms_index_manager.refresh()`，并单独记这一段耗时。调用前检查 `VERSION()` 是否达到 seekdb 1.3.0。解析失败就不调用，页面会说明，避免 SDK 静默跳过还被当成已经刷新。刷新后再做一次探针，探针时间不计入检索延迟。重复 id 会跳过，新 id 追加。换库以 seekdb 里的集合为准。

## 性能表

五次评测都在同一台机器的 Microsoft Edge 156.0.4314.42 上完成，显卡是 NVIDIA GeForce RTX 4060，显存 8GB。WASM 那一行用 `?device=wasm` 强制单线程 WASM，另外两行页面报告 WebGPU。10 篇样例、10 条查询、k=5、`rankWindowSize=40`、`rankConstant=60`。浏览器用 `performance.now()`。`seekdbSearchMs` 只包服务端那一次 `hybridSearch`。端到端从发起查询到结果返回。预热后对第一条查询重复 5 次，下表取中位数。

| 配置 | 模型体积 | 查询向量化中位数 | seekdb 检索中位数 | 端到端中位数 | Recall@5 / nDCG@5 |
| --- | ---: | ---: | ---: | ---: | --- |
| FP32 + WebGPU | 94851877 字节 | 8 ms | 13 ms | 50 ms | 1.000 / 1.000 |
| INT8 + WebGPU | 24010842 字节 | 85 ms（复测 83） | 13 ms | 124 ms（复测 122） | 1.000 / 0.889 |
| INT8 + WASM | 24010842 字节 | 17 ms（复测 17） | 12 ms（复测 9） | 56 ms（复测 53） | 1.000 / 1.000 |

模型加载读数：FP32 6868 ms，INT8 WebGPU 426 ms（复测 486 ms），INT8 WASM 455 ms（复测 475 ms）。INT8 这几次很可能吃到了已经下好的文件，不能把四百多毫秒对 6868 说成加载快十几倍。查询向量化换成单条吞吐：FP32 约 125 次/秒，INT8 WASM 约 59 次/秒，INT8 WebGPU 约 12 次/秒。这是一条短查询，不是一批文档的吞吐。文档写入和 `refresh_index` 的分阶段耗时不在这些 JSON 里。第一次 WASM 里 `q-ocean` 的端到端出现过 272 ms，是单次卡住，中位数仍是 56 ms。复测没有这条毛刺。

seekdb 检索中位数在 9 到 13 ms，精度和后端没有把数据库耗时拉开。INT8 把体积压到约 1/3.95。在这条单线程 WASM 上，这 10 条查询的 Recall@5 和 nDCG@5 都没降，查询向量化比 FP32 WebGPU 慢一倍左右。界面报 WebGPU 的 INT8 又更慢，而且 nDCG@5 降到 0.889。这台机器上，INT8 换来的是更小的模型文件，不是更快的查询。
