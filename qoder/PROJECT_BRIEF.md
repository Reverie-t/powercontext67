# 科研周报助手

## 作品目标

面向需要定期提交实验室周报的科研人员，把分散的实验、文献阅读、问题与待办整理为有出处、可修改、可导出的周报，并在下一次使用时继续使用已保存的研究方向、汇报偏好和未完成事项。

## 赛事与交付约束

- 代码仓库：https://github.com/Reverie-t/powercontext67
- 基线分支：`2026-competition-ecosystem`
- 本次开发分支：`qoder-research-weekly`
- 所有项目资产放在 `qoder/` 中，不修改其他赛道。
- 主要应用开发必须通过真实 Qoder CN 会话完成，保留会话标识、执行记录与验证结果。不得把其他工具的开发记录写成 Qoder 记录。
- PowerContext 必须真实参与记忆保存、读取与后续生成；本地 JSON、浏览器存储或接口模拟不能替代此项验收。
- 项目网站通过 Qoder Sites 发布，公开可访问；网站可作为介绍、操作演示和本地完整功能运行说明的入口，不要求把 Python 服务放到静态托管环境。
- 最终提交字段是完整 Commit ID、Branch 和公开作品链接。只有代码确已推送、站点确已发布并检查后，才能给出可提交值。
- 不包含真实密钥、密码、个人实验资料或虚构使用效果数据。示例研究内容必须标明是合成样例。

## 首版完整流程

1. 建立研究项目并保存研究方向、周报语言、汇报偏好。
2. 以日期和类型添加实验记录、文献记录、问题和计划；每条保留稳定编号与原始文本。
3. 选择一周的日期范围，读取本周原始记录，以及 PowerContext 中同一项目的偏好和未完成事项。
4. 生成可编辑的 Markdown 周报，包含本周进展、阅读总结、问题与风险、下周计划，每个事实可对应原始记录或记忆引用。
5. 预览并导出 Markdown；保存确认后的计划，下一周可以继续使用，并明确区分已完成与未完成事项。
6. 证据页显示真实 PowerContext 读写、作用范围、引用以及它们如何用于生成。故障需要明确展示，不能默默退回模拟数据。

## 实现建议与工程要求

技术栈由执行开发的 Qoder 根据实际依赖和 Sites 能力选择，优先考虑 Python 3.11+、轻量 HTTP 服务和无需构建或轻量构建的 Web 前端。本地运行不应强制要求模型 API Key。可以提供可复现的规则整理模式；若提供大模型增强，单独说明配置、生成模式和来源限制。

优先使用固定版本的 PowerContext 正式 Python 包及其 SQLite 持久化和显式 Memory API，先运行最小真实写入与重启读取验证，再构建业务功能。可读取同级 `../powercontext/` 的源码、README 与 Jupyter 示例了解 API，但不得依赖该目录才能复现。依赖必须列出准确版本，不能将类名或 HTTP 路径猜测成真实接口。

公开站点若只有静态运行环境，提供明确标识的交互合成演示、真实本地运行证据及完整安装步骤；演示中不声称实际调用 PowerContext。所有 PowerContext 功能需要在完整本地项目中可复现。

界面应以科研记录和周报阅读为中心：清楚的主操作、充足正文宽度、明确日期和保存状态、键盘可操作、可读的错误提示、窄屏布局。禁止编造统计、用户评价或实验结论。

## 交付内容

- 可运行应用、固定依赖、占位配置与从零安装说明。
- 公开项目展示站点的源码与 Qoder Sites 发布说明。
- 合成的两周初始数据与一键验证入口。
- 真正验证 PowerContext 跨客户端、跨进程持久化的验收测试；项目隔离和日期边界验证。
- 真实运行证据，注明环境、命令、生成模式与已知限制。
- Qoder 开发记录：只记录实际执行的会话、任务与文件；不得凭空生成对话截图、账号 UID 或部署结果。
- 提交清单，最终值由实际 Git 和 Qoder Sites 返回结果填写。

## 验收通过条件

从全新项目开始保存偏好，写入第一周记录并生成周报；退出并重启程序后，不重新输入偏好，在第二周生成结果中可看到偏好和第一周未完成任务确实被读取、引用并使用。项目 B 不得读到项目 A 的记忆。生成内容不能把没有完成证据的计划写成已完成成果。公开站点必须能在未登录状态打开。
